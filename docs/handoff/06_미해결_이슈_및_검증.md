# 미해결 이슈·회귀 테스트·릴리스 수용 기준

**기준 시점: 2026-09-30 / 원본 v0.15.1.** 이 파일은 문제를 숨기지 않고 다음 채팅에서 재현·수정할 수 있게 기록한 것입니다.

## ISSUE-001 — EOS RP CR3 이미지 분석 중단 (최우선)

### 사용자가 제공한 재현 조건

- 입력: Canon EOS RP `IMG_8284.CR3`, ISO 1600, 노출 133.2초, 해상도 6264×4180, RGGB.
- Siril: Windows x86_64 ucrt64 CLI **1.4.4**.
- 입력 로그에 `RAW Decode: Siril/LibRaw + Debayer`, RAW 전용 staging 폴더 `cd`, `convertraw` 성공.
- Siril 변환 FITS: RGB 3채널, 6264×4180, 16-bit; 이후 `analysis_input.fits` 저장 성공.
- `jsonmetadata` JSON 출력/스크립트 완료 로그까지 확인되지만 `이미지 분석 완료` 또는 최종 Python 오류는 제공된 로그에 나타나지 않는다.
- 헤더는 `BITPIX=16`, `BZERO=32768`, `BSCALE=1`.

### 유력한 코드 수준 문제 — 원인 추정, 아직 traceback 없음

`astroauto/analyzer.py:analyze_input_file()`은 Siril 메타데이터 수집 후 `analyze_pixels()`를 호출한다. v0.15.1 `astroauto/fits_analysis.py`의 `analyze_pixels()`는 아래처럼 읽는다.

```python
with fits.open(path, memmap=True, do_not_scale_image_data=False) as hdul:
    hdu = next((h for h in hdul if getattr(h, "data", None) is not None), None)
```

16-bit FITS의 `BZERO/BSCALE` 스케일링이 필요할 때 Astropy의 이미지 데이터 memmap 경로가 실패할 수 있다. 재현된 Python traceback이 없으므로 이를 **가장 유력한 가설**로 기록한다. `read_header_summary()`도 `memmap=True` 및 `hdu.data` 접근이 있어 같은 계열의 위험이 있다.

### 수정 및 수용 테스트

1. 적절한 FITS 픽셀 읽기 경로에서 `memmap=False`를 적용하고, Header 분석도 스케일링 키와 호환되도록 처리한다.
2. 임시로 생성한 unsigned 16-bit(`BITPIX=16, BZERO=32768, BSCALE=1`) RGB FITS로 `analyze_pixels()`/`read_header_summary()` 회귀 테스트.
3. 기존 2D 단색 및 일반 32-bit float FITS의 분석 결과가 유지되는지 확인.
4. 원본 RAW bytes와 채널·방향·해상도를 비교하고 실패 시 원본이 변하지 않는지 확인.
5. Windows 실사용에서 `IMG_8284.CR3 → 이미지 분석 완료 → 프로젝트 생성`을 검증. 오류가 재발하면 **Python traceback 및 이후 로그**를 확보하여 가설을 재검증.

## ISSUE-002 — 실제 FITS bit depth와 정규화 계약 불일치

- v0.15.0 명세/`input_formats.py`의 설명과 반환 metadata는 작업용 `32-bit float`를 목표로 한다.
- 사용자가 제공한 Siril 로그에서는 `set32bits` 실행에도 `astroauto_raw_00001.fits`, `analysis_input.fits` 모두 **16 bits**로 저장됐다.
- 이는 `set32bits` 명령이 저장 FITS의 실제 `BITPIX=-32`를 보장했는지 추가 확인이 필요한 상태다. 분석 단계 실패의 독립 원인으로 단정하지 않는다.
- 목표 테스트: RAW 단일 변환 후 FITS 실제 Header `BITPIX` 검사, 픽셀 보존/범위/원본 정밀도 검토. 메타데이터 `precision` 문자열도 실제 파일과 일치하도록 보장.

## ISSUE-003 — Siril `jsonmetadata` 통계 채널명 깨짐

- 사용자 로그의 `statistics`에 `"\u0000\u0000\u0000\u0000nel2"` 같은 비정상 키가 반복된다.
- 현재 앱은 `siril_metadata`를 보고서에 보존하며 자체 픽셀 통계는 `analyze_pixels()`로 별도 계산한다. 이 키를 ISSUE-001의 직접 원인으로 취급할 근거는 아직 없다.
- 확인: 원본 `siril_metadata.json`의 키/채널 개수, Siril 1.4.4 JSON 생성과 동일 이미지의 다른 버전 비교, 필요하면 앱 측 안전한 채널명 별도 지정.

## ISSUE-004 — 대용량 분석·Windows 런타임

- `analyze_pixels()`의 `_sample_evenly()`는 샘플링 전에 입력을 float64로 평탄화·정리한다. 대용량 RGB 입력에서 순간 메모리 사용이 커질 수 있다.
- 이는 **잠재적 품질 개선 항목**이며 제공된 로그만으로 메모리 부족이 있었다고 판단하지 않는다.
- 메모리 부담 테스트, 채널 단위 제한 샘플링, 취소 가능성은 실제 병목이 확인되면 진행한다.
